RelayIQ Placement API v2 Contract

Status: Placement API v2 Draft 4 - implemented

Scope: standalone placement API; legacy v1 and scheduler behavior remain separate

Purpose: allow an independent agent harness to request a policy-backed execution target class and its requirements.

POST /v2/placement/decide

1. Endpoint behavior

RelayIQ's Judge classifies the supplied input and request context, including whether this specific request requires caller consent for cloud use and which types of sensitive data it detects. RelayIQ then evaluates one operator-controlled policy snapshot, applies caller constraints, and returns a bounded placement recommendation. The response recommends one of local, cloud, cloud_with_consent, or fallback.

Consent is a per-request Judge decision, not an operator-wide cloud setting. The endpoint does not invoke an answer model, execute tools, manage provider credentials, alter the caller's conversation, or return a sanitized payload. The caller remains responsible for redacting sensitive data before cloud transmission, obtaining consent, selecting a specific suggested model, executing it, and handling retries or fallback.

A valid request normally returns HTTP 200 even when no model execution is permitted. In that case target_class is "fallback" and fallback_action tells the caller whether local execution is allowed or processing must stop.
This is a breaking revision from Draft 3. Draft 4 removes context.redaction_profiles, requirements.redaction_profile, policy setting supported_redaction_profiles, and reason code REDACTION_UNSUPPORTED. Under the strict request schema, sending context.redaction_profiles returns HTTP 400 with INVALID_REQUEST. Producers and consumers require coordinated updates. The standalone runtime, generated OpenAPI, checked-in policy configuration, and docs/relayiq-v2-poc.md implement Draft 4. Migrate existing policy files to the profile-free shape with a new revision; old files fail strict startup validation. The v2 Judge path publishes the expanded classification structure; the legacy Judge interface and deterministic fallback routing are unchanged. suggested_models is now a two-lane object, not the earlier flat array. DECISION_UNAVAILABLE is retired and never returned. An unavailable policy or failed policy evaluation returns HTTP 500, not a fallback decision.
This v2 response intentionally does not contain the v1 fields placement, policy, permitted_payload, or requires_consent. The legacy v1 endpoint remains a separate API surface.

2. Request

Send a strict JSON object using Content-Type: application/json. Unknown fields and type coercion are rejected.

Example

{
  "input": "Review confidential employee data for alex.example@example.com and compare two architecture options for storing it.",
  "preferred_target_class": "cloud",
  "model_mapping": {
    "local": ["phi-4-mini"],
    "cloud": ["nvidia/nemotron-3.5-lightning-30b-a3b"]
  },
  "context": {
    "connectivity": true,
    "cloud_budget_kb": null,
    "required_capabilities": ["extended_reasoning"]
  }
}

Suggested model inventory

When present, suggested_models contains exactly local and cloud, each an array of non-blank strings, unique within its own lane. The same model name may appear in both lanes. Neither lane may be omitted or null. The earlier flat-array form is invalid.

These lists describe caller-provided inventory, not permission or availability. A local recommendation still includes the caller's cloud models even if cloud is excluded by policy, connectivity, or budget. Likewise a cloud recommendation includes the caller's local models. Only the recommended lane must be non-empty. Follow target_class, consent requirements, and fallback_action; do not execute an unselected lane merely because its models are listed.

Requirements fields

FieldTypeRequiredInvariant
consent_requiredbooleanYes Must be true exactly for cloud_with_consent and false for every other target. The Judge determines it from the prompt and request context.

Classification fields

classification reports the Judge's assessment of the input and request context, not the final placement decision. When present, it contains exactly the five fields below, each required and a strict JSON boolean. Missing fields, extra fields, strings, numbers, and null are invalid. Do not infer these flags from the selected target or substitute defaults for unavailable Judge output.

FieldTypeMeaning when true
routinebooleanThe Judge assesses the request as routine, straightforward work.
fresh_knowledgebooleanA correct answer requires current or up-to-date information.
reasoning_heavybooleanThe request requires deep or substantial multi-step reasoning.
criticalbooleanThe request concerns an immediate real-world threat to physical health, life, or safety.
sensitive_databooleanThe Judge detected data within its active sensitivity scope in the input or request context. The current relayiq-judge-v1 scope is email addresses only.

These are classification signals, not mutually exclusive target classes. This contract does not define routine as the negation of another flag. Policy and caller constraints still determine placement. critical does not authorize cloud disclosure, and sensitive_data does not replace requirements.consent_required.

For healthy classification, classification.sensitive_data is true if and only if SENSITIVE_DATA_DETECTED and a non-empty sensitive_data_types array are returned. When it is false, omit both the reason code and category field. For CLASSIFIER_DEGRADED, omit the entire classification object as well as both sensitivity findings; do not report unavailable sensitivity as false. These rules apply to all completed decisions, including local and fallback. Error envelopes remain unchanged.

Sensitive-data classification rules

The current relayiq-judge-v1 Judge uses LLM-based email detection: return a positive sensitivity finding only when at least one actual email address is detected in the input or supplied context. Positive findings use exactly ["email_address"], once even for multiple addresses. Names, social security numbers, employee IDs, phone numbers, financial data, confidential text, and mentions of email without an address do not independently trigger the finding. An email alongside other data still qualifies. Out-of-scope positive categories or invalid model assessments produce CLASSIFIER_DEGRADED with findings omitted, not a fabricated negative. Consent remains independent and may be required for non-email confidential data. This scope does not narrow the caller's redaction or disclosure obligations.

sensitive_data_types describes the types of sensitive data the Judge detected in the supplied input and request context. Each value is a non-blank snake_case identifier matching ^[a-z][a-z0-9]*(?:_[a-z0-9]+)*$. The vocabulary is extensible: email_address is the only category emitted by the current Judge. Future Judge versions may add categories such as social_security_number or employee_id; these are not a closed enum. Callers must tolerate additional category identifiers. Values must be unique; array order has no semantic significance.

Return only category labels, never detected values, snippets, personal identifiers, or offsets. The field is present if and only if reason_codes contains SENSITIVE_DATA_DETECTED. It must not be null or an empty array, and no unavailability sentinel is used.

AssessmentSENSITIVE_DATA_DETECTEDsensitive_data_typesCLASSIFIER_DEGRADED
Healthy, sensitive data detectedPresentNon-empty unique category arrayAbsent
Healthy, no sensitive data detectedAbsentOmittedAbsent
DegradedAbsentOmittedPresent

CLASSIFIER_DEGRADED is mutually exclusive with both SENSITIVE_DATA_DETECTED and sensitive_data_types, even if a heuristic suggests a category. Omission does not guarantee that the input is safe; for degraded classification it means sensitivity findings are unavailable, not that no sensitive data exists. Sensitivity findings describe the request independently of the selected target, including local or fallback. They do not themselves select cloud, change the consent invariant, or introduce a new automatic fallback rule.

4. Selection and fallback behavior

OutcomeEligibility and meaningRequired relationships
local Local is policy-permitted and, when a mapping is supplied, the local lane contains at least one model. consent_required is false. If suggestions are present, suggested_models.local is non-empty and cloud preserves the caller's cloud list.
cloud Cloud is policy-permitted, has inventory when mapped, has connectivity, and fits the request budget. consent_required is false. If suggestions are present, suggested_models.cloud is non-empty and local preserves the caller's local list.
cloud_with_consent The cloud lane is eligible and the Judge determines from the prompt and request context that explicit approval is required. consent_required is true. If suggestions are present, suggested_models.cloud is non-empty and local preserves the caller's local list.
fallback A known policy was evaluated, but neither desired nor alternative target is eligible, or policy explicitly blocks model use. consent_required is false; suggestions are omitted when no mapping was supplied, otherwise {"local":[],"cloud":[]}. Policy blocks require stop. Policy unavailability is HTTP 500, not fallback.

RelayIQ first chooses the desired class from preferred_target_class, when present, or from classifier/policy routing. It selects that class if eligible; otherwise it tries the other class. If neither class is eligible, it returns fallback.

fallback_action: "local" is returned only when local failure handling is permitted by policy and a local candidate is eligible for the relevant outcome. Otherwise the action is "stop".

6. POC policy snapshot

The checked-in config/relayiq-policy.json defines the profile-free policy below. policy_revision identifies an operator-assigned immutable snapshot, not the API draft number. Operators must assign a new revision when changing a deployed snapshot; relayiq-judge-v1 is the current revision and accompanies the email-only Judge scope.

SettingValueEffect
policy_revisionrelayiq-judge-v1Reported on decisions made with this snapshot.
permitted_targets["local","cloud"]Both target classes may be selected when eligible.
local_failure_permittedtrueEligible local execution may be offered as a fallback.
deny_inputs["Demonstrate the configured demo block."]An exact match returns POLICY_BLOCKED and fallback/stop.
Judge-reported categories are not a guarantee of complete sensitive-data detection or successful redaction. An invalid configured policy fails service startup. If no policy path is configured, a valid placement request returns HTTP 500 with INTERNAL_ERROR before invoking the Judge. A policy evaluation failure also returns HTTP 500, regardless of local fallback permissions.

7. Validation and failure behavior

ConditionHTTP resultResponse semantics
Valid request, including bounded fallback outcomes200A contract-valid placement decision is returned.
Malformed JSON, missing input, unknown field, wrong strict type, explicit null optional, duplicate/blank model, or out-of-range/non-finite budget400INVALID_REQUEST; no decision is created.
Policy unavailable, policy evaluation failed, or unexpected internal endpoint failure500INTERNAL_ERROR; no decision or fallback recommendation is returned.
Placement service temporarily cannot produce any decision503SERVICE_UNAVAILABLE; no decision is created.

Error envelope

{
  "error": "INVALID_REQUEST",
  "message": "Missing required field: input.",
  "decision_id": null
}

Policy unavailable or evaluation failed (HTTP 500)

{
  "error": "INTERNAL_ERROR",
  "message": "The placement service could not complete the request.",
  "decision_id": null
}

Every 400, 500, and 503 response uses exactly error, message, and decision_id. The stable error code is one of INVALID_REQUEST, INTERNAL_ERROR, or SERVICE_UNAVAILABLE. The message is diagnostic text and is not a machine-readable decision signal.

RelayIQ logs decision metadata such as decision ID, policy revision, target class, reason codes, and elapsed time. Request text, exception text, and credentials are not part of the routine endpoint log contract.

8. Caller obligations

  1. Treat target_class, fallback_action, reason_codes, and conditional classification and sensitive_data_types as the machine-readable decision surface. Classification signals do not override placement or consent requirements.
  2. For either cloud outcome, use reported categories to guide the caller's own redaction of sensitive data before transmission. RelayIQ neither performs nor verifies that redaction and supplies no sanitized payload or locations of sensitive values. For cloud_with_consent, obtain approval before invoking the selected model; consent is not proof of redaction.
  3. Accept new category identifiers without treating them as non-sensitive. A missing category field does not guarantee safety, especially with CLASSIFIER_DEGRADED. The caller remains responsible for assessing and handling data safely before cloud transmission.
  4. For a normal recommendation with suggestions, choose from suggested_models.local for local, or suggested_models.cloud for either cloud target. The other list is inventory only, not authorization to switch lanes. RelayIQ does not execute the choice.
  5. Honor fallback_action: "stop" by not invoking an answer model under this decision.
  6. Handle transport errors and error envelopes as no usable decision; do not infer placement from human-readable text.

9. Integration and acceptance criteria

The API validates Judge output and exposes the same rules through OpenAPI. Invalid or incomplete model assessments use the degraded response shape, without substituting default classification flags. Callers must migrate to Draft 4 before integration; the following criteria define the supported boundary.

  • Accept a profile-free request; reject the removed request field as an unknown field under Draft 4.
  • Return only consent_required in requirements; do not use profile matching to determine cloud eligibility.
  • Enforce all three assessment cases in the classification matrix, including omitting sensitivity findings whenever CLASSIFIER_DEGRADED is present.
  • Return all five strict boolean classification fields for healthy classification and omit the object for degraded classification. Keep classification.sensitive_data, SENSITIVE_DATA_DETECTED, and sensitive_data_types consistent.
  • Return only unique category labels for positive detections; accept an extensible vocabulary without exposing sensitive values.
  • Omit suggestions without a request mapping; otherwise return both lane arrays, preserve their order for normal recommendations, and empty both arrays for fallback.
  • Return HTTP 500 with the error envelope when policy is unavailable or evaluation fails; never emit DECISION_UNAVAILABLE or a success-shaped fallback for these failures. Successful decisions always contain a non-blank policy_revision.
  • Preserve target/consent relationships, policy bounds, connectivity, budget, inventory, preferences, fallback, and error envelopes.
